Two behaviours in these rows are the version's, not a tier's:

- **The mission's tool loop runs to its per-turn cap far more often.** With thinking off, the bf16 run on
  0.27.1 made 77 tool calls over the twelve turns and every turn ended with a reply; on the port the same
  cell made 144 calls with six turns ending at the 16-call cap and an empty reply (int8: 172 calls, nine
  capped turns). On the capped turns the model polls the same two tools repeatedly (`telemetry sps` and
  `request_evaluation sps`, seven times each on turn two) instead of answering the turn's question, which
  0.27.1 answered directly with no tool call. Scores survive because the scorer credits decisions made on
  later turns; the wall time on int8 doubles. Diagnostic cells are queued (the same cell with prefix caching
  off, with speculation off, with MTP, and int4 with prefix caching off) to find which layer of the port
  changes this. The tool-call parser is the same on both versions (`qwen3_coder`).
- **Judgment misses D6/D7 (arm, then get Houston's go before the final log) on six of eight rows** (int4 with
  thinking off misses D3/D4 instead, as it did on 0.27.1). On 0.27.1 the D6/D7 pair is missed on some rows and
  not others; on the port the model does not arm at all on those rows. Same family as the point above: the model's behaviour in the tool loop, not the decision logic.
- Thinking on: the port's reasoning traces are shorter per turn (288 to 6,285 characters on bf16 against
  1,458 to 14,190 on 0.27.1), so walls drop with thinking on; the int8 thinking-on pair does not reproduce
  itself (13 then 15), the first non-reproducing pair on this port.

### The collapse, reproduced in a fresh container: KVarN + DFlash2 on the port

The KVarN + DFlash2 cell (start_qwen.sh `CTX=huge SPEC=dflash2`, depth 7, prefix caching on, no connector)
fails the mission the way the int4 production server failed it on 0.27.1 with the offload connector: turn one
is fine (13 tool calls, GO for TLI), then from turn two every reply is `duct Register Register Register...`
to the 900-token cap (`finish_reason=length`, repeat ratio 1.00), and the last turn is symbol soup; 8/18 in
725 s. The string is character-identical to yesterday's collapse. Its judgment run took 97 s where every other
tier's took 12 to 26 s. Same image with MTP instead of DFlash2: clean (15/18 twice; 18/18 with thinking on).
0.27.1 on the same cell yesterday: 16/18 and 18/18. So on the port the collapse is reachable with no connector
at all, on KVarN with DFlash2, from the second turn over a shared prefix. Single-shot probes do not see it
(the boot matrix's count probe passes on this cell; a second machine's four-prompt probes pass on three of
four and flip the structure of a short JSON answer at depth 7). This is the maintainer's "wrong output"
cell, with the failure shape named: a Mamba-state collapse on the second turn, not a token swap. The
localisation ladder now runs the mission on this cell with prefix caching off, the fused verify off, lookup
drafting off, the adaptive length off, at depth 15, with speculation off, a repeat, and the same cell on the
0.27.1 image as the control.

### Two machines on the KVarN cell

Same mission, same launcher and settings, only the drafter changed. The second machine is a native RTX 3090
under Ubuntu (a venv install of the same branch, no container).

| machine | KVarN + MTP | KVarN + DFlash2 | shape of the DFlash2 failure |
|---|---|---|---|
| RTX 4090, WSL2, container | 15/18, 15/18 (50 s) | 8/18, 9/18 (725 s, 748 s) | "duct Register" repeated to the cap from turn two |
| RTX 3090, native, venv | 15/18 (77 s) | 3/18 (203 s) | the same string, ten of twelve replies, from the first reply |

One symptom on both machines (an earlier reading of the second machine's row as "coherent but failing" came
from scanning the bench's console output, which carries scores and tool calls but no reply text; the trace
file has the collapse string throughout, and that reading is withdrawn). The MTP rows are identical across
the machines, so the benches, launchers and pools are equivalent and the DFlash2 gap is the port's. The
score difference (3 against 8 or 9) is how far the scorer gets before the replies stop being usable. On the
second machine the block-aligned-hits marker was present on all seven of its DFlash2 cells and absent on all
six MTP or no-speculation cells, and the depth-7 JSON divergence on a short prompt reproduced byte-identically
across runs, which is what a deterministic aligned-down continuation would do.

Diagnostic hunks so far (both on this branch under `patches/`, unapplied drafts): suppressing KVarN's
pre-forward flush and reclaim on a wide cached continuation starves the staging pool on the 4090 (engine
dead, "KVarN pool exhausted (32 slots)", eighteen requests in); the flush-only variant applies cleanly on
both machines, does not heal the collapse on the 3090 (3/18 to 3/18, the string still present), and on the 4090 stalls
the engine: 32 requests in, one request running at zero tokens per second indefinitely, no fatal; on the
3090 the same variant completes the whole mission with the score unchanged (3/18, 204 s against 203 s).
So the flush is what frees staging slots on the machine where it stalls, the lifecycle timing is
environment-sensitive in the same way the collapse symptom is, and the fix has to handle the aligned-down
continuation correctly rather than skip a step.

## The connector arm per tier

The 0.27.1 engine-death recipe: the offloading connector, the pool pinned near the working set, and a side-load
of long prompts so the conversation's blocks leave the GPU between turns and come back from CPU. On 0.27.1 every
tier died in the scheduler within minutes; on the port:

| tier | pool | reload batches during the run | engine | mission |
|---|---|---|---|---|
| int4 + DFlash2 | 36,739 | 73 | alive, no assert | 12/18, every turn coherent (judgment misses, not repetition) |
| int8 + DFlash2 | 31,200 | 40 | alive, no assert | 15/18 |
| bf16 + DFlash2 | 20,264 | 21 | alive, no assert | 15/18 (its no-connector score) |
| KVarN + MTP | 57,079 | 14 | alive, no assert | **2/18**: coherent text, the model insists the tracking tool is not available to it (15/18 without the connector) |

Reading: the 0.27.1 engine death does not occur on the port on any tier, and int4, int8 and bf16 keep their
no-connector scores under 21 to 73 reload batches. KVarN does not: with MTP, fourteen reloads are enough for
the model to lose the tool definitions that live in the system prompt's blocks, a different shape from the
repetition collapse: coherent text with lost knowledge rather than a repeated token. Put beside the KVarN + DFlash2
collapse here, both KVarN failures on the port are blocks re-entering KVarN's staging pool from outside the
normal write path (a reload from CPU, or an aligned-down re-prefill over a shared prefix), and the other tiers,
which write through stock slot mappings, do not have the failure. For the offload goal this means: on the
port the CPU offload connector is usable with int4, int8 and bf16, and not with KVarN until KVarN's residency
lifecycle handles re-entering blocks.

### The instrument speaks: what turn two actually recomputes

The third diagnostic routed the wide continuation through KVarN's slow attention path (fp32 SDPA over gathered
history) with the lifecycle untouched. Not healed: 7/18, the same string from turn two, ten of twelve replies
cut at the cap. The attention consumer is exonerated. But the debug gate that rode with it fired 246 times,
and the first prefix-hit request of turn two reads, on this machine:

```
seq_len=1553 query_len=657 committed=896
blocks k=7..12 = physical 840..845, every one slot=None flush=False
```

The conversation is 1,553 tokens and the previous turn ended near 1,540, but the hit is honoured only to 896,
a scheduler-block boundary (neither the 128-token KVarN block nor the true hit). The 657-token remainder is
recomputed as one continuation, and every block it writes into is one KVarN has already flushed to permanent
int4 and released from its fp16 pool (`slot None`). On later turns the pattern repeats: committed stays at 896
or 1,344 while the sequence grows. The int4 tier writes the same rows through stock slot mappings and simply
overwrites them; KVarN has no staging slot for a block it considers finished, and where those rows land is
the poison site. Two threads follow from this: what KVarN does with a write into a slotless block (the fix),
and why the hit stops at 896 on the port when 0.27.1 hit at the true boundary (the cause). The int4 tier's
tool-loop capping is the same continuation seen without corruption: with prefix caching off, int4 answers
turn two directly and caps one turn instead of six; bf16 with MTP caps nine turns, so the capping does not need
DFlash2's drafter group, only the port's prefix-cache resume.
