Scope: I reviewed the fork-side unified diffs and this week's validation record. The installed vLLM 0.28 rejection sampler is not present in this checkout, so sampler behavior not exposed by those files is marked UNVERIFIED.

1. **The renormalisation reading is conditionally right, but the proposed sign argument is wrong.** The kernel first normalises `scores / temperature` only to calculate the top-p mask, then replaces rejected logits with negative infinity; it does not store those temporary probabilities (`patches/dflash2-lookup-drafting.patch:207-215`). It stores the resulting logits as `realized` (`patches/dflash2-lookup-drafting.patch:225-232`) and later sends that score buffer through the draft-logit cache path (`patches/dflash2-lookup-drafting.patch:478-497`, `patches/dflash2-lookup-drafting.patch:518-520`). If upstream obtains q by softmaxing those cached logits, q must be renormalised over the finite kept entries. Nothing in the fork can restore the removed denominator because the removed logits and any original normalising constant are not retained. The actual upstream logits-to-q operation is **UNVERIFIED** here. The fork only states its expectation that the sampler consumes pre-temperature logits (`patches/dflash2-lookup-drafting.patch:439-442`), while this week's installed-tree read reports that 0.28 applies temperature only to the target side (`docs/v0.28-validation.md:697`); at T=1 this disagreement is inert.

   More importantly, this code does not remove tokens by inspecting the target's support. It computes rank and cumulative mass from the draft's `scaled_scores` (`patches/dflash2-lookup-drafting.patch:207-214`). Applying the same numeric top-k and top-p settings separately to p and q does not make their token supports equal. A token removed from q can be supported by p, and a token kept by q can be absent from p. The registered no-sign prediction is therefore defensible, but not for the stated reason. Also, a lower `p/q'` on a kept draw does not by itself predict lower average acceptance because q' changes how often that draw occurs. If the removed set really had zero p mass, the overlap `sum min(p, q')` could only increase after conditioning q onto that set's complement. The possible negative sign comes from draft-target ranking disagreement, not from renormalisation alone.

2. **Yes, there is another host-side gate, plus an effective overwrite.** The environment flag is read with an exact string comparison to `"1"` (`patches/dflash2-lookup-drafting.patch:287-291`), and `TRUNCATE` is passed true only when that flag is true and `_req_top_p` has been installed (`patches/dflash2-lookup-drafting.patch:454-474`). The setter installs both request buffers (`patches/dflash2-lookup-drafting.patch:444-446`), and the merged runner calls it (`patches/dflash2-lookup-drafting.patch:989-995`), so this fourth gate should be satisfied on this tree, but a generic resolved engine-config print is not proof that this direct environment read or `draft_logits` is live. Log `self._truncate`, `selector_top_k`, request top-k/top-p, and `draft_logits is not None` explicitly. Inside the kernel the remaining visible gates are probabilistic drafting, nonzero request temperature, and `TRUNCATE` (`patches/dflash2-lookup-drafting.patch:203-215`); probabilistic drafting is compiled from `self.draft_logits is not None` (`patches/dflash2-lookup-drafting.patch:470-474`).

   There is also an effective exposure gate after the selector. Lookup runs after the selector and cache (`patches/dflash2-lookup-drafting.patch:518-524`) and rewrites every lookup-used proposal row to a point mass (`patches/dflash2-lookup-drafting.patch:567-585`, `patches/dflash2-lookup-drafting.patch:799-820`). Truncation may have executed on such a row, but none of its q survives to rejection. Count only drafter-carried rows when reporting truncation exposure. The optional chain path is default-off (`patches/dflash2-ngram-chains.patch:1`, `patches/dflash2-ngram-chains.patch:44-47`); confirm it remains off.

3. **Cell E alone is not worth the boot.** The fork documents a 16-candidate selector (`drafter/README.md:102-104`), and the rank predicate is `rank < req_top_k` (`patches/dflash2-lookup-drafting.patch:211-215`), so top-k 20 cannot remove one of those candidates. Top-k 8 makes the rank predicate capable of firing, but comparing E with A also changes the target distribution from top-k 20 to top-k 8. That is not an on/off estimate of draft truncation. If the rank effect matters, run a matched pair: E with truncation on and F with truncation off at the same top-k. Set top-p to 1.0 in both if the purpose is to isolate the rank half. A top-k of 15 is the smallest ordinary perturbation that can remove a candidate, but top-k 8 gives more exposure and likely more power.

   The cheaper answer to "did the rank or top-p test execute?" is not another throughput boot. Add a shadow counter or one debug probe that reports eligible selector rows, rows with at least one removal, candidates removed by rank and by top-p separately, and q mass removed. That also rescues A/B: without those denominators, an A/B null cannot distinguish no activation from no value. Drafted tokens per round is a block-length measure, not a truncation-activation measure; the current validation record reaches the same conclusion for arm 3 (`docs/v0.28-validation.md:792`).

4. **As proposed, a null would be uninterpretable for both power and state reasons.**

   First, eight prompt-seed rows are not enough for a registered absolute effect below 0.15 tok/step. The prior paired cohort had 32 rows (`docs/v0.28-validation.md:738`) and observed a 0.290 difference with t=2.77 (`docs/v0.28-validation.md:742`). Those numbers imply a paired-row standard deviation near 0.59 tok/step. At that variance, eight rows give an approximate 95 percent half-width of 0.41, and roughly 60 independent paired rows are needed merely to shrink that half-width to 0.15. Use at least eight seeds by eight prompts, paired by prompt and seed, state an interval or equivalence rule in advance, and budget extra rows for guard exclusions and within-boot clustering. Output-token count does not turn one prompt-seed trajectory into hundreds of independent samples.

   Second, fixed request order is necessary here but not sufficient. The adaptive lookup policy retains `_prev_want` and `_sticky` across steps and can coast the long block (`patches/dflash2-lookup-drafting.patch:415-433`). This week's direct order experiment found that request order changed drafts and accepted tokens on four of six seeds, including one trajectory moving from 31 to 112 verify rounds (`docs/v0.28-validation.md:780`). Because truncation can change generated text, it can change suffix matches and the state handed to the next request. Thus the same nominal order need not produce the same pre-request state across A and B. For a mechanistic A/B, disable lookup. For a production total-effect A/B, counterbalance or randomise request order across multiple boots and treat boot/order as blocking factors; do not claim paired per-request equality. Setting sticky to zero alone does not reset `_prev_want` or remove within-request lookup mediation.

   Third, measure exposure before stratifying. Record eligible drafter rows, kept counts, removed q mass, lookup-overwritten rows, actual verify rounds, actual completion tokens, and per-position denominators. The validation record already shows that cumulative per-position counts confound how often a position existed with how often it accepted (`docs/v0.28-validation.md:788`). Do not infer a per-step truncation effect from drafted-tokens-per-round averages, and do not stratify on a block length that the treatment can change. The degeneracy guard-before-stratification rule is correct and is empirically necessary (`docs/v0.28-validation.md:750`), but it does not solve post-treatment stratification.

   Finally, send temperature, top-p, top-k, and seed explicitly in every request and print that payload. The current cohort command only requests a custom output length and prompt count (`bench/prefill_ab.sh:74-77`), while the current DFlash2 launcher line in this checkout omits `draft_sample_method` (`single-user/start_qwen.sh:231-232`). The arm's explicit field fixes the known no-op, and C/D are a useful harness control, but C/D cannot prove that top-p removed anything at T=1. Require C/D identity and measured A/E mask activation as separate validity checks.

VERDICT: boot with changes: instrument truncation exposure, isolate or counterbalance lookup state, expand to at least 64 paired prompt-seed rows, and replace E with a matched E/F pair
