1. **Renormalisation: the fork supplies masked logits, not normalised probabilities. The expected renormalisation is real, but the upstream consumer remains UNVERIFIED.**

   The kernel computes probabilities from temperature-scaled scores solely to construct the mask, replaces rejected entries of the original scores with negative infinity, then passes those scores to `gumbel_noised_argmax` and stores `realized = scores` (`patches/dflash2-lookup-drafting.patch:203-231`). It declares a float32 draft-logit cache with negative-infinity initial values and calls the cache routine after walking the selector (`patches/dflash2-lookup-drafting.patch:439-442`, `patches/dflash2-lookup-drafting.patch:518-520`). There is no retained-mass compensation in these added lines. Assignment to `realized` itself does no normalisation.

   Conditional on the consumer softmaxing this row, write the original proposal as q and the kept support as S, with Z = sum over S of q. Then q_S(i) = q(i)/Z for i in S and zero otherwise. A vocabulary-wide softmax has the same result as a softmax over the kept candidates because exp(-infinity) is zero. Normalising elsewhere therefore implements this renormalisation; it does not cancel it. At fixed target probability p(i), min(1, p(i)/q_S(i)) cannot increase for a surviving token. The sampling helper and rejection sampler implementations, including any additional filtering and their actual acceptance formula, are **UNVERIFIED** here. This is a mathematical consequence of the stated sampler contract, not an inspected upstream implementation.

   Do not promote the patch's temperature comment to evidence about upstream: it says the rejection sampler divides cached logits by temperature (`patches/dflash2-lookup-drafting.patch:225-227`, `patches/dflash2-lookup-drafting.patch:439-440`), while this week's notes report an installed-source read finding that only target logits receive temperature scaling (`docs/v0.28-validation.md:697`). That disagreement is harmless at T=1 but is another reason to keep this arm at T=1 and mark the consumer UNVERIFIED. A short installed-engine probe should compare the q actually read with a reference softmax of the masked row.

   **The requester's support argument is wrong, even though leaving the sign unpredicted is appropriate.** The mask uses the drafter's candidate scores and their cumulative mass, not target probabilities (`patches/dflash2-lookup-drafting.patch:207-215`). Matching numerical top-k/top-p settings does not imply matching support. It can remove tokens with positive target probability and retain tokens with zero target probability.

   Moreover, under the stated rejection rule, expected single-proposal acceptance is alpha(p,q) = sum_i min(p(i), q(i)). If the removed tokens really all had p(i)=0, truncation could not lower alpha: removed terms were zero and every retained q increases. The falling conditional p/q test alone is not a countervailing aggregate effect. The possible loss here comes from removing useful target mass. For example, at top-p .95, q=(.96,.04) becomes (1,0): acceptance rises from .96 to 1 if p=(1,0), but falls from 1 to .96 if p=q. These are mathematical examples, not measurements. Neither argument predicts the sign of tokens per step across a changing autoregressive trajectory.

4. **The present cohort cannot support an informative null without activation, a defined state policy, and an uncertainty target.**

   First, this is not merely a hypothetical objection: the current validation notes already describe arm 3 as halted for unmeasured activation and unequal state under fixed request order (`docs/v0.28-validation.md:792`). Register the redesign before restarting. Without measured removals, a null can mean the mechanism did nothing on these rows. Even with removals, it can mean lookup erased them or early rejections hid them. It cannot establish that top-p truncation is generally worthless.

   Fixed request order controls one input, not the state produced by preceding outputs. The policy reads delayed flags, requires consecutive qualifying steps, and carries sticky state; lookup reads each request's token history (`patches/dflash2-lookup-drafting.patch:415-433`, `patches/dflash2-lookup-drafting.patch:534-546`). Order effects persisted with prefix caching actually disabled in this week's experiment (`docs/v0.28-validation.md:780-782`). Disabling the cache alone is not a reset.

   Choose the estimand explicitly. For a direct drafter-mechanism comparison, use lookup off, chains off, and verify width seven, with matched prompt/seed schedules and equal warmup. Pinning width matters: with lookup off the patch otherwise asks the drafter for the full configured width, rather than clamping it to the trained block (`patches/dflash2-lookup-drafting.patch:54-59`). For a production pipeline comparison, retain production lookup but treat each complete, identically initialised request sequence as the experimental unit. Output-dependent lookup differences are then part of the treatment effect. Replicate sequences; do not call their individual rows independent or call their difference a pure renormalisation effect. A validated full policy reset between requests is another option; merely clearing the sticky counter is not equivalent to resetting the other state shown at lines 415-433.

   Keep the degeneracy guard before stratification, but preregister it, report failures by arm, and preserve paired comparisons if either member fails. A treatment-dependent collapse must remain a reported outcome. Freeze any stratum labels from an independent baseline before treatment. The prior cohort's split used baseline block size, and one collapsed row previously flipped the overall sign (`docs/v0.28-validation.md:738-750`). Do not split each arm by its own observed block size or select only identical-output survivors. The teacher-forced harness explicitly warns that clean-only selection excludes uncertain, lower-acceptance continuations (`bench/labd_accept.py:53-56`).

   Define R as verification rounds, A as accepted draft tokens, and N as drafted tokens submitted. Report raw deltas and the identities `tok/step = 1 + A/R`, `drafted/round = N/R`, and `acceptance = A/N`. Thus `tok/step = 1 + (A/N)(N/R)`; an acceptance-per-token change cannot be compared directly with the 0.15 tokens-per-step threshold. The local benchmark uses the rounds and accepted-token counters for this primary ratio (`bench/labd_bench.py:60-64`, `bench/labd_bench.py:140-142`). Verify the installed counter semantics and reconcile with actual emitted tokens and end-of-request boundaries. Preregister whether the cohort statistic is a mean of paired request ratios or a pooled ratio; the local benchmark's total pools counts (`bench/labd_bench.py:148-160`), which weights rows by rounds.

   Eight prompts times a 1024-token cap is not a power calculation. Specify the number of paired seeds, record actual output lengths and finish reasons, and do not count correlated output tokens as independent replicates. Seeds must vary across replicates and match across A/B. Native-box identical-seed repeats previously replayed identical counters (`docs/v0.28-validation.md:730`). As a planning warning only, the earlier 32-pair cohort's difference of 0.290 with t=2.77 implies a standard error near 0.105 under that analysis (`docs/v0.28-validation.md:738-744`). That precision would not even put a zero-centred 90% interval inside +/-0.15. Arm 3 may have different variance; measure paired pilot variance and size the run accordingly, accounting for shared prompt or session state. Define equivalence as a prespecified confidence interval wholly inside +/-0.15. A small point estimate or failure to reject zero is not equivalence.

   Treat C/D as a short functional negative control, with identical initial state and fixed kernels, rather than two full power-sized cells. Their truncation body is bypassed at T=0 (`patches/dflash2-lookup-drafting.patch:203`); that establishes a kernel no-op, not equal wall-clock time across boots. Any output/counter mismatch needs explanation before A/B, but equal C/D does not demonstrate A/B activation. Print resolved request sampling, draft-logit presence, attached buffers, selector width, block widths, lookup/chain policy, graph configuration, and engine/patch identity before results. Measure decode time and time per round alongside acceptance: a throughput arm can lose speed while gaining tokens per step.
