1. **Question 1: neither target breadth nor draft confidence follows from 80.1% acceptance. Being the best draft position does not determine the effect of truncation.**

   Acceptance, confidence, and entropy are different quantities. Under the usual probabilistic rejection rule, fixed-context expected acceptance is `alpha(p,q) = sum_i min(p_i,q_i) = 1 - TV(p,q)`. An acceptance of 0.801 describes overlap, not the drafter's maximum probability or either distribution's entropy. Here this formula remains conditional on the installed sampler implementing the contract discussed in round 2; its implementation is UNVERIFIED. Lookup further prevents treating the reported acceptance as a pure selector statistic: the visible code copies selector proposals, applies lookup, and can replace their cached distributions with point masses (`patches/dflash2-lookup-drafting.patch:518-524`, `567-585`, `799-821`).

   A verified prefix removes one possible source of context error. It does not imply `H(p) > H(q)`, calibrated confidence, or matching token rankings. Nor does the assertion that the drafter is best at position zero establish any of those properties. The visible selector calculates its mask from its own temperature-scaled scores, without a target-distribution argument in that calculation (`patches/dflash2-lookup-drafting.patch:203-215`). Target breadth at position zero is a hypothesis requiring measurement, not an expected property established here.

   There is a direct counterexample to the coordinating seat's "cannot help" claim, compatible with an eight-token target support. Let S be the drafter's top eight, let their original mass be `Z = 0.801`, and let the target distribution be exactly `p = q_S`, the proposal renormalized on S. Acceptance is 0.801 before truncation and 1 afterward. This position could already have the highest acceptance of all positions. The improvement does not require changing the prefix or correcting the top-ranked token. This is an algebraic example, not a measured selector row.

   High baseline acceptance limits upward headroom, so a well-matched position can plausibly have less to gain. That is weaker than predicting harm. Removing useful overlap can dominate at that position, but the supplied counts do not establish that it did. Also, the new table does not show an identical early shape: position one gains 47 under the top-p cut and loses 9 under the rank cut. The common observation is a position-zero loss and positive late sums, not a replicated position-by-position mechanism.

2. **Question 2: eight removed candidates can carry almost no mass. Measure the mass before masking; the acceptance loss has a useful bound.**

   For a fixed context define q as the untruncated distribution over the selector's candidates at the actual sampling temperature, S as the actual kept set, and `epsilon = sum_outside_S q = 1 - Z`. This is selector probability mass, not a percentage of candidate IDs or the mass of the draft model's vocabulary head. The current code computes normalized probabilities from selector scores, uses ranks and cumulative mass to mask them, then retains masked original logits in its output buffer (`patches/dflash2-lookup-drafting.patch:207-215`, `225-232`). The post-mask buffer alone cannot recover epsilon.

   Even assuming exactly eight of sixteen finite candidates survive, epsilon can approach zero or, for a nearly uniform row, one half. Nothing about 80.1% acceptance selects a value in that interval. Moreover, "exactly eight by construction" still needs qualification: rank counts strictly greater scores, so boundary ties can retain more; the top-p predicate still executes at top-p=1 and has no bypass in the visible calculation (`patches/dflash2-lookup-drafting.patch:211-215`). Granting the requester's exact-count premise does not grant a nonnegligible epsilon.

   Under the same fixed-context rejection contract, the relevant decomposition is:

   ```text
   L = sum_outside_S min(p_i, q_i)
   G = sum_inside_S [min(p_i, q_i/Z) - min(p_i, q_i)]
   D = alpha(p,q_S) - alpha(p,q) = G - L
   0 <= L <= epsilon;  0 <= G <= epsilon;  abs(D) <= epsilon.
   ```

   Thus removed TARGET mass alone is also the wrong proposed mediator. A removed token can have substantial target probability but negligible q probability, making its lost overlap negligible. Retained-support gain must also be subtracted from the loss. If epsilon is tiny on the relevant position-zero rows, the direct expected acceptance effect is tiny on those same contexts. An unweighted ranking-disagreement count cannot repair that bound.

   The raw -32 is not yet a violation of it. On matched N contexts the expected direct loss cannot exceed `sum epsilon`, but realized counts fluctuate. Free-running arms also need not have the same contexts or N. Fewer rounds can reduce accepted position-zero counts even while increasing total accepted drafts through longer blocks. Obtain the position-zero submitted denominator before translating -32 into an acceptance-probability loss. The local metrics client separately reads rounds, submitted draft tokens, accepted tokens, and per-position accepted totals; its request bracketing differences counters rather than calculating an intrinsic per-position probability (`bench/labd_accept.py:112-145`, `255-270`). The installed producer semantics remain UNVERIFIED.

   A narrowly defined support-disagreement condition does survive: if p has no support outside S, then L is zero and fixed-context expected acceptance cannot decrease. Under an eight-token target cutoff, identical kept target and draft supports therefore exclude direct loss. But disagreement is not sufficient for loss, and its ordinal extent does not determine `L - G`. Define p after the target's actual temperature, filtering, and other sampling transformations; the installed target processing for these runs is UNVERIFIED. Raw target entropy or raw-logit ranks are not automatically properties of that p.

This establishes the visible branch's behavior, not the absence of bugs elsewhere in an unavailable engine. Also distinguish switching the draft flag within tr-E/tr-F from comparing the earlier top-p regime to the rank regime: the request parameters differ across regimes, so equal target policies across those two experiments are not an available assumption.

   **Consequence (a): plausible dependence, no causal attribution from these totals.** Later target contexts can change through the proposed prefix. There is also acceptance-prefix dependence even if target logits are held fixed: under sequential rejection, counting acceptance at position j requires reaching it after earlier acceptances. Higher late counts can reflect different exposure or prefix composition, without a higher conditional acceptance probability at j. Actual metric implementation is UNVERIFIED, as detailed in question 4. The observed position-zero loss particularly does not demonstrate a "better-supported early proposal." Under exact speculative sampling, changing the proposal should preserve the target output law; individual seeded trajectories and block boundaries can nevertheless differ. Position zero has a common verified prefix only in a matched-context comparison, not automatically across every free-running round.

   **Consequence (b): reject the sign argument.** The position-zero counterexample in question 1 already disproves "cannot help." Later uncertainty does not establish that removed proposals would all have been rejected. Only `p_i = 0` guarantees rejection for a removed candidate under the stated rule; a positive p/q can accept a tail proposal. The mask never consults p (`patches/dflash2-lookup-drafting.patch:203-215`). Calling the top candidate "usually right" substitutes an argmax story for probabilistic acceptance. Under the stated rule, even when a surviving proposal token stays unchanged, renormalizing q changes its conditional acceptance probability `min(1,p_i/q_i)`. Changing token context is therefore not the only available mechanism.

   **The entropy prediction is not a consequence of that path.** For a point target `p = delta_t`, target entropy is zero. If t is removed, truncation changes acceptance from `q_t` to zero. If t is kept, it changes acceptance from `q_t` to `q_t/Z`, an improvement. These limiting examples give opposite signs at the same target entropy. A peaked target on a token the drafter misranks is a counterexample to "near zero where target is peaked." Entropy does not locate target mass relative to S.

   **One logprobs field is not a specified falsification test.** A sampled token's negative logprob is surprisal, not the distribution's entropy; a partial top-logprobs list omits an unknown tail. A single initial-prompt value also does not characterize the many verified prefixes that later become draft position zero. A request average discards that alignment. The visible client requests `logprobs: 0` and extracts token IDs, without computing entropy or preserving speculative-step identities (`bench/labd_accept.py:166-191`). The requester's proposed field and its raw-versus-processed semantics are UNVERIFIED.

   The number of JSON fields is not the limitation: one field could contain complete per-step probability arrays and identities. All normalized target support probabilities, or a correctly computed entropy scalar for every relevant frozen prefix, could support a preregistered entropy association test. At rank k=8, all eight processed target probabilities would suffice for entropy if they really exhaust support. Many correctly sampled logprob observations can also estimate an average entropy under specified weighting; one sampled logprob cannot reveal it. Neither an entropy association nor an exact entropy scalar measures target-draft support disagreement. Specify prefixes, probability semantics, denominators, and the quantitative predicted relationship before calling the present proposal falsifiable.

   The proposed rule needs correction: **Python side effects inside captured work observe capture; captured GPU operations can observe the live run on every replay.** Not necessarily once per boot, either: different graph shapes, warmups, and recaptures can enter Python multiple times. A Python list holding references to reused GPU buffers is not a per-step history. CPU/GPU synchronization such as `.item()` is incompatible with capture; CPU logging is not replayed. These general distinctions are also documented in [NVIDIA's CUDA graph guidance](https://docs.nvidia.com/dl-cuda-graph/latest/torch-cuda-graph/best-practices.html#writing-cuda-graph-compatible-code).

   There is a concrete counterexample to the blanket "inside means invalid" rule in this patch: `_lookup_hits` is device storage, and the fuse kernel executes `tl.atomic_add(hits_ptr, ...)` inside the documented captured region (`patches/dflash2-lookup-drafting.patch:330`, `745-746`, `777-781`).
