# vLLM 0.28 port validation review

## Round four

### 1. The logged `slot=None` is pre-allocation, not the store target

CONFIRMED: the round-three interpretation of the debug tuples was wrong. The
gate was inserted before the flush at installed-backend lines 845-869 and,
critically, before allocation at lines 879-914. Thus `slot: None` says that the
physical block lived in packed int4 on entry to the metadata build. It does not
say where `do_kv_cache_update` writes later.

The exact transition is: every block from `committed // GROUP` through
`(seq_len - 1) // GROUP` is added to `blocks_needed` at lines 675-696. After
flush/reclaim, line 881 tests `bid not in dict_map`; lines 908-911 pop a fresh
pool slot, install `dict_map[bid] = slot`, and write that slot into the GPU
`b2s_t` lookup. `do_kv_cache_update` then launches the scatter at lines
2166-2183. The final fate is decided in
`v1/attention/ops/triton_kvarn_decode.py:127-129`: a genuinely negative
`pool_slot` returns and drops the row; otherwise lines 136-141 write fp16 into
the staging pool. It never treats the packed int4 tile as fp16 storage.

For the supplied tuples, therefore, the blocks are reintroduced as write
targets during build. While their new fp16 slots are live, consumers follow
`b2s_t` and ignore the old packed tiles. A later `_batched_flush` quantizes the
completed fp16 `[GROUP, Hk, D]` tile and `_write_packed` replaces the block's
packed K/V payload and scales/zero-points. The packed tile is unchanged between
allocation and that later flush, then becomes the quantization of the newly
staged rows. The observed corruption is real, but these pre-allocation tuples
do not locate its poison site.

### 2. Why the port resumes at 896

CONFIRMED from the active geometry: KVarN's block is 128 tokens and the aligned
Mamba state page is 448 tokens. Sliding-window groups are excluded from the
scheduler LCM by `kvarn/kvarn-v2-runner-0.28.0.patch:65-80`, so the promoted
2,176-token DFlash group does not participate. The remaining fixed point is
`lcm(128, 448) = 896`; 1,344 is three Mamba pages and is likewise an available
Mamba checkpoint, though not a multiple of 896.

The launcher explicitly requests a 128-token hash unit at
`single-user/start_qwen.sh:500-504`. In 0.28, however, the coordinator disables
fine-grained partial lookup when `SlidingWindowManager` cannot represent the
hash-aligned hit and its physical block differs from the hash unit. Lookup then
aligns to the scheduler/Mamba-reconstructible boundary, explaining 896 rather
than the approximately 1,536-token 128-grid match. The 0.27.1 fork patched the
hybrid resolver/SlidingWindow handling differently
(`../qwen38-main/kvarn/kvarn-v2-runner.patch:1-34,176-245`) and the reported
configuration did resume at 1,536. Therefore the loss of hit precision belongs
to the 0.28 coordinator/SlidingWindow contract, but a wide valid continuation
still must be safe in KVarN.

### 3. Smallest KVarN-side test patch

RECOMMENDATION: use re-staging, option (b), not skipping. KVarN is not told the
true byte-identical hit; `committed` is the scheduler-approved boundary. It
cannot safely distinguish redundant recomputation from new tokens, so option
(a) could retain unrelated packed rows. Re-staging is already the intended and
actual control flow. The draft at
`patches/kvarn-continuation-flushed-blocks.draft.patch` makes the ownership
transition explicit: it records newly allocated blocks, clears reused fp16
slots, and retains the debug gate with a post-allocation block-to-slot line.
It is deliberately small enough for the mission run and applies after the
round-three diagnostic with `patch -p1 -d site-packages/vllm`.

The decisive next log is paired pre/post output: each pre-allocation
`slot=None` continuation block must have a nonnegative `post_allocate` slot. If
it does, rows are not dropped at the scatter guard and clearing should be a
no-op for every fully rewritten block; a healed mission would implicate stale
rows in a partial re-stage. If it does not, the allocator/lookup publication is
the defect. If every mapping is live and the mission remains 7/18, instrument
the first later flush with a fill count/checksum rather than changing the
attention consumer again.

## Round three

### 1. Slow-path diagnostic and lifecycle semantics

CONFIRMED: suppressing both flush and reclaim exhausted the 32-slot KVarN pool
after 18 requests, while suppressing only flush stalled after 32 requests. Those
results rule out skipping the lifecycle as a viable fix and show that flush is
required to turn staging tiles into reclaimable slots. The unpatched RTX 4090
still changes from a correct first turn to capped `duct Register` repetition on
turn two. The native RTX 3090 instead retains coherent text but falls to 3/18,
while MTP is 15/18 on both machines. The supplied runtime observations are
CONFIRMED experiment results; their internal cause remains unproven.

CONFIRMED: `patches/kvarn-continuation-slow-path.draft.patch` is an unapplied
diagnostic against the installed backend and is suitable for
`patch -p1 -d site-packages/vllm` (`patches/kvarn-continuation-slow-path.draft.patch:1-12`).
It adds a metadata flag only when a request
has cached context and its query length exceeds `reorder_batch_threshold`, as
derived by the builder at
`kvarn/files/vllm/v1/attention/backends/kvarn_attn.py:592-620,994-1003` and
`patches/kvarn-continuation-slow-path.draft.patch:13-78`.
Forward routes only that wide continuation to `_decode_path_slow`; narrow
speculative verifies and fresh prompt chunks retain their existing routes at
`kvarn_attn.py:2251-2268` and
`patches/kvarn-continuation-slow-path.draft.patch:80-99`.

CONFIRMED: `_decode_path_slow` does not bypass KVarN's fp16 pool and does not
materialize continuation rows into that pool before the flush queue can see
them. Flush detection and `_batched_flush` run in the metadata builder before
forward at `kvarn_attn.py:767-868`. The cache update later writes current K/V
through the already assigned pool mapping. The slow consumer then calls
`_gather_request_kv`, which reads blocks with slots from `_tail_K_pool` and
`_tail_V_pool`, reads slotless full blocks by dequantizing int4, and constructs
temporary fp16 request tensors at `kvarn_attn.py:2337-2393`. It runs fp32 SDPA
over those temporaries at lines 2427-2460. By contrast,
`_cached_multiquery_path` builds rotated fp16 K/V in the shared FlashAttention
scratch buffers with `_kvarn_build_packed_kv_kernel` at lines 2539-2641 and
consumes them with FlashAttention at lines 2643-2659. Therefore this A/B tests
the history reconstruction and attention consumer, not the pre-forward
lifecycle decision.

### 2. One corrupted-state fact that fits both machines

PLAUSIBLE: the single shared fact is that the first turn-two verify reads one
physical history block through the wrong KVarN residency mapping: its block id
resolves to a pool slot whose rows do not belong to the accepted prefix for that
block. The corrupted logical state is the same on both machines. Immediate slot
reuse on the RTX 4090 can make that stale tile strongly self-reinforcing and
produce deterministic repetition, while different allocator timing or reuse on
the RTX 3090 can leave less adversarial rows and cause coherent but substantial
capability loss. The hardware-dependent contents are PLAUSIBLE, not confirmed;
Python set/pop order, request timing, and CUDA allocation history must also be
held constant before attributing reuse specifically to the GPU model.

The draft's `KVARN_CONTINUATION_DEBUG=1` gate emits one aggregate line in the
builder after flush and reclaim decisions are known but before `_batched_flush`
mutates residency. For every recomputed block of a wide cached continuation it
prints request row, sequence length, query length, committed boundary, block-
table index, physical block id, current pool slot, and whether that block is in
the flush set (`patches/kvarn-continuation-slow-path.draft.patch:23-59`). This
location corresponds to the decision assembled at
`kvarn_attn.py:794-843` and precedes the mutation at lines 845-869. Comparing
the two machines' first prefix-hit line identifies the first exact `(k, block,
slot, flush)` tuple that differs. If those tuples are identical, this hypothesis
shifts from mapping divergence to different contents already resident in the
same slot, which requires a bounded checksum or generation counter in the next
run.

### 1. Classification, causal lengths, and KVarN commit

CONFIRMED: KVarN initializes `reorder_batch_threshold` with
`supports_spec_as_decode=True` at
`kvarn/files/vllm/v1/attention/backends/kvarn_attn.py:434-444`. The builder
passes that threshold to `split_decodes_and_prefills` at lines 592-598. Thus a
depth-7 verify query of at most 8 tokens is decode-classified, while a resumed
prefix suffix wider than 8 is prefill-classified. The 0.28 V2 runner additionally
rejects a uniform decode count whenever `batch_state.has_prefill` is true at
`kvarn/kvarn-v2-runner-0.28.0.patch:207-221`. The 0.27 runner used its older
request-state guard at `kvarn/kvarn-v2-runner.patch:337-358`.

CONFIRMED: `KVarNMetadata.is_prefill` is independently set from
`cam.max_query_len > 1` at `kvarn_attn.py:1005-1016`. For a pure width-8 verify,
the builder emits one causal length per token as
`seq_len - query_len + j + 1` at lines 943-970, and forward selects the fused
verify path at lines 2251-2258. For a block-aligned continuation wider than 8,
`num_decodes == 0`, `has_cached_multiquery` is true by lines 994-1003, and
forward selects `_cached_multiquery_path` at lines 2259-2268. That path does not
emit `vq_seqlen`. It passes the real `query_start_loc` to FlashAttention at
lines 2539-2551 and 2650-2657, whose bottom-right causal mask supplies causal
limits equivalent to `committed + j + 1`.

CONFIRMED: the cache lifecycle uses the exact query length. It computes
`committed = seq_len - query_len` when selecting every block written by the
step at `kvarn_attn.py:675-696`. Before the forward writes the new K/V, it walks
backward only through blocks wholly below that committed boundary at lines
767-815. It then flushes those fp16 pool tiles into permanent int4 storage and
reclaims their shared slots at lines 845-868. `do_kv_cache_update` writes the
continuation only later; its no-flush contract is documented at lines
2121-2186. The permanent-poison site is therefore the pre-forward flush queue
at lines 794-815 feeding the batched quantizer at lines 845-868, with the actual
packed write in `_batched_flush` at lines 1947-2032. A wrong committed boundary
there freezes stale or speculative rows into int4 and every later decode reads
them.

CONFIRMED: on the source as checked in, a correctly reported block-aligned
continuation is not deliberately discarded and is not incorrectly included in
the current build's flush. Its recomputed blocks are added to `blocks_needed`
at lines 675-696 and allocated at lines 869-914. Consequently the code trace
does not prove an arithmetic off-by-one. The remaining KVarN-specific risk is
the lifecycle transition itself: a formerly cached/slotless physical block is
reintroduced as a write target while the same build flushes or reclaims other
pool state before those recomputed rows exist.

PLAUSIBLE: that transition corrupts one KVarN tile on the resumed step, after
which every width-8 verify has internally consistent but wrong history. This
fits the deterministic turn-two cliff and repetition loop. It is not yet
confirmed because the repository has no GPU trace of `flush_block_ids`, block
IDs, and slot mappings for that step. In 0.27.1 fine-grained hits began at the
true hit, so the additional aligned-down span did not reintroduce these blocks.
The KVarN implementation is otherwise source-identical across the checkouts.

### 2. Why int4 per-token-head survives

CONFIRMED: the int4 tier uses stock vLLM cache ownership and direct per-token
packed-cache writes. Its local patch only fixes padded cache views and carries
DFlash's causal controls into the packed attention kernel:
`patches/int4-kv-per-token-head.patch:54-83,85-104,106-170`. It has no KVarN
fp16 tail allocator, `_block_fill`, pre-forward flush, or permanent whole-tile
commit decision. The 0.27 copy has the same functional hunks at
`../qwen38-main/patches/int4-kv-per-token-head.patch:54-170`.

CONFIRMED: both tiers therefore receive the same aligned-down scheduler suffix,
but int4 overwrites the scheduled token slots through normal vLLM slot mapping.
KVarN first maps every touched physical block into its private fp16 pool at
`kvarn_attn.py:675-696,869-914`, then later converts completed blocks wholesale
to its private packed format at lines 1947-2032. Only KVarN has a separate
commit boundary capable of making a transient continuation error permanent.

### 3. Origin of the gate and smallest GPU hunk

CONFIRMED: the warning gate is upstream vLLM 0.28.0 code, not a port hunk. In
the 0.28.0 source, `HybridKVCacheCoordinator` disables partial hash hits when a
manager reports no fine-grained support and its block size differs from the
hash unit, then selects scheduler-block alignment instead of hash-block
alignment. The installed wheel reports this at `kv_cache_coordinator.py:645`.
The local port does not add that coordinator gate. Its related hunk only turns
an unsupported SlidingWindow lookup into a clean miss at
`kvarn/kvarn-v2-runner-0.28.0.patch:126-135`.

CONFIRMED: `patches/hybrid-sw-block-promote.patch:52-102,146-152` promotes a
small sliding-window drafter page to a larger physical block. That makes the
upstream predicate observable: `SlidingWindowManager` still declares no
fine-grained lookup support and its promoted block differs from the hash unit.
The 0.27 fork's corresponding promotion has additional divisor handling at
`../qwen38-main/patches/hybrid-sw-block-promote.patch:73-162`, but merely
regenerating promotion does not implement partial SlidingWindow lookup.

CONFIRMED: making SlidingWindow fine-grained honestly requires more than
removing the veto. The manager must map a hash-aligned logical hit to all
physical blocks covering its rolling window, preserve block-table positions
with null padding, retain those physical blocks for every registered boundary,
and keep EAGLE tail-drop semantics correct. Bypassing the coordinator alone can
claim a shared computed-token boundary for draft KV that the SlidingWindow
group cannot reconstruct.

PLAUSIBLE: the production fix belongs in KVarN first. A valid scheduler
continuation is normal input, and KVarN must tolerate it regardless of why the
coordinator selected that boundary. The smallest low-risk diagnostic is saved,
unapplied, at `patches/kvarn-block-aligned-continuation.draft.patch`. It suppresses
KVarN flush and reclaim only on a cached continuation wider than the reorder
threshold. Allocation and writes still occur. The next ordinary verify build
sees those rows as committed and may flush them only after they have actually
been written. If the turn-two collapse disappears, the pre-forward lifecycle
is confirmed; then log and narrow the exact offending block instead of keeping
the broad guard. If it does not, the next A/B is to force that one continuation
through `_decode_path_slow`, because the remaining differentiated path is the
materialize plus FlashAttention continuation at `kvarn_attn.py:2539-2659`.

## 1. DFlash2, KVarN, and verify-state advance

### CONFIRMED

The checked-in KVarN implementation, including `v1/attention/backends/kvarn_attn.py` and `v1/attention/ops/triton_kvarn_decode.py`, has no content difference from `../qwen38-main/kvarn/files`. The port patches change integration APIs and runner/cache geometry, not those two implementation files. The 0.28 base patch describes its API conversion at `kvarn/kvarn-0.28.0.patch:1-3`; its packed-page reshape branch is at `kvarn/kvarn-0.28.0.patch:224-233`. The 0.27 equivalent uses `TQFullAttentionSpec` at `kvarn/kvarn-0.27.1.patch:213-242`.

KVarN's builder computes exact CPU sequence lengths from the private `_seq_lens_cpu` cache, falling back to a device-to-host copy at `kvarn/files/vllm/v1/attention/backends/kvarn_attn.py:599-608`. It computes query lengths from `query_start_loc_cpu` at lines 609-618. The fallback at lines 619-620 is `[1] * len(seq_lens_cpu)`. That fallback is valid only for single-token decode.

Those query lengths drive the verify state. At `kvarn/files/vllm/v1/attention/backends/kvarn_attn.py:943-970`, the builder detects multi-token decode, computes `committed = seq_len - ql`, and emits one causal length per verify token. It zeroes every unfilled tail row at lines 971-977. The per-token fused path then consumes this plan at lines 2462-2485. The alternate eager path independently computes `committed` from device query starts at lines 2510-2517.

The fused verify kernel contract is explicit: `vq_seqlen` is one causal length per query token (`kvarn/files/vllm/v1/attention/ops/triton_kvarn_decode.py:876-898`). Its shared-dequant kernel likewise expects a per-token plan and reads the last token's entry as the request length (`.../triton_kvarn_decode.py:1056-1064,1092-1102`). The shared path is disabled unless `KVARN_SHARED_VERIFY=1` (`.../triton_kvarn_decode.py:935-946`), so it is not the default-path explanation.

The 0.28 V2 compatibility patch changes only the model-runner classification around the verify path. It derives `batch_state.has_prefill`, asks upstream for a uniform decode count, then rejects that count when prefill remains (`kvarn/kvarn-v2-runner-0.28.0.patch:207-221`). The 0.27 patch performed the analogous guard by comparing runner request-state arrays (`kvarn/kvarn-v2-runner.patch:337-358`). Neither hunk advances KVarN's per-token verify plan.

The Mamba state-copy port is different because upstream 0.28 moved the relevant inputs. The 0.28 hunk loads `num_computed`, derives query length from `query_start_loc`, computes `computed_after`, then selects the source state and accepted-token offset (`patches/mamba-chunked-prefill-align.patch:40-57`). The earlier 0.27-targeted form shown by commit `db0603e` used a scalar `qlen`; this file does not exist in the dfee877 patch set. Both forms use `src_off = max(num_accepted - 1, 0)`. The KVarN runner patch separately seeds the resumed Mamba state with the Mamba spec block size at `kvarn/kvarn-v2-runner-0.28.0.patch:161-175`, matching the 0.27 port's intent at `kvarn/kvarn-v2-runner.patch:275-294`.

The regenerated DFlash2 backport retains the absolute-length update: `out_seq_lens = min(last_valid_pos + 1 + num_query_per_req, max_model_len)` at `patches/dflash2-backport.patch:295-302`; the 0.27 stack has the same operation at `../qwen38-main/patches/dflash2-backport.patch:291-299`. This is not a source-level divergence.

### PLAUSIBLE

The most likely defect is the silent one-token fallback at `kvarn_attn.py:619-620`. If the 0.28 V2 DFlash2 `CommonAttentionMetadata` instance lacks `query_start_loc_cpu`, or no longer exposes it under that name, KVarN treats a k-wide verify as one token. The loop at lines 961-970 fills only one plan row per request; lines 975-977 zero the other k rows. The per-token verify kernel then uses causal length zero for those rows. This predicts a width-dependent failure isolated to KVarN's fused verify, while ordinary bf16/int8 attention and one-token KVarN decode remain unaffected. It also explains why k=15 fails more severely than k=7.

I could not inspect the installed wheel because no venv exists here. I verified the public v0.28.0 tag's scheduler source, but not the exact built wheel nor runtime object attributes. Therefore the absence of `query_start_loc_cpu` on the failing DFlash2 batch is not confirmed. The measured MTP success is evidence against a universal metadata failure; DFlash2 may construct or reuse metadata through a distinct V2 route.

The next candidate is an accepted-token timing mismatch in `preprocess_mamba_align_fused_kernel`: `src_off` comes from `num_accepted`, while the destination column comes from scheduler-side `num_computed + query_len` (`patches/mamba-chunked-prefill-align.patch:44-56`). That could select a recurrent state from the wrong verify offset when async DFlash2 and the scheduler are one step apart. It is less likely because it should affect non-KVarN tiers unless the 128-token KVarN block geometry is required to trigger the copy boundary.

### 1. The gate arithmetic rules out 910bbf2 for the single-request failures

### 2. What split-K changes, and what numerical hazard the file actually shows

CONFIRMED: the one-stage and split stage-1 kernels use the same data path. Both
map a virtual query row through `Req_row_ptr` when `VQ_INDIRECT` is true, load
that row's causal length, walk the request's block table, choose the fp16 pool
or packed cache, dequantize K and V with the same formulas, and compute the same
masked dot products. Compare the one-stage body at
`docs/.installed_triton_kvarn_decode.py:387-500` with split stage 1 at lines
553-642.

There is no accumulator-width difference in this file. Both use fp32 `q`,
`m_i`, `l_i`, and `acc` (`:417-423` and `:578-583`). The inner tile loop and
address arithmetic are the same. The packed V stride is `D // PACK_V` in both
paths (`:481-485` and `:623-631`). Block and pool offsets use int64 in both
paths (`:438-445` and `:588-594`). Both kernels have the same
`[Q_PER_KV_PAD, D]` live accumulator, so the source does not identify a
verify-only shared-memory or register-spill threshold. The file documents
register-limited occupancy as a performance issue at lines 42-50, not as a
correctness mechanism.

The only actual numerical distinction is reduction shape. One stage carries a
single fp32 online-softmax state through every block and normalizes once at
lines 421-502. Split stage 1 limits each state to a contiguous block slice,
writes fp32 partial output plus log-sum-exp at lines 567-651, and stage 2
combines the partials with another fp32 log-sum-exp reduction at lines 654-682.
That changes rounding and shortens each serial rescale chain. It can produce
finite last-bit differences, but the file supplies no overflow, loop-bound,
indirect-index, shared-memory, or accumulator-width defect that turns those
differences into wrong logits. Its own comments say the reduction-order effect
is only fp noise and the split count does not change output at lines 42-50 and
60-71.

The unchecked use of raw `block_id` in `tile_base` after only masking the
block-to-slot lookup is worth noticing at lines 438-445, but split stage 1 does
the identical thing at lines 588-594. It therefore cannot explain one-stage
bad versus split-K good. The explicit NaN guards also exist in both paths at
lines 491-500 and 635-642.

READING: the comment at lines 984-990 reports an observation, not a cause
demonstrated by this kernel. From this file alone, the only supported candidate
is ordinary fp32 online-softmax reduction-order sensitivity. There is no
identified numerical hazard of the requested stronger kinds. More decisively,
the failing single-request cells already use split-K, so even a real one-stage
hazard is not the cause of their collapse.

### 3. The plain decode path shares the one-stage arithmetic

CONFIRMED: for `B * Hk > sm_count`, the plain decode heuristic declines its
automatic split and launches the exact same `_kvarn_fused_decode_kernel` at
`docs/.installed_triton_kvarn_decode.py:766-808`. The only relevant constexpr
difference is `VQ_INDIRECT=False` at lines 748-764. Plain decode therefore uses
`bt_row = b` and one sequence length per request, while verify uses
`Req_row_ptr[b]` and one causal length per query token at lines 387-405. All
dequantization and online-softmax arithmetic after that selection is shared.

Consequently, an accumulator, long rescale-chain, tile-loop, packed-address,
or spill defect in the one-stage body also exists for wide-batch plain decode.
A truly verify-specific defect must instead involve the virtual-row plan or its
per-token causal lengths. For this one-request cell every `vq_req` entry is
zero, so even the block-table indirection has only one possible row; the causal
length staircase remains the substantive verify-only input. Split stage 1
consumes the same `vq_req` and `vq_seqlen`, however, at lines 560-569.

READING: the passing `SPEC=off` single-request arm does not exercise the
wide-batch one-stage case. With `B=1`, `B * Hk = 4`, so ordinary decode also
automatically takes split-K under this deployment-constant block bound. MTP's
15/18 result is evidence against a universal KVarN failure, but it does not
make 910bbf2 applicable to DFlash2: both small single-request verify widths fit
below the SM count and already split. The code supports a verify-plan or

### 2. The verify-step sequence lengths

Let `C` be the accepted count at the start of a target step, `Qprev` the
previous target query length, and `Rprev` the number rejected from that query.
The next accepted count is

`Cnext = C + Qprev - Rprev`.

In vLLM 0.28, the post-sampling update applies exactly that delta in
`v1/worker/gpu/input_batch.py:548-558`. On the next step,
`prepare_pos_seq_lens` receives the corrected `num_computed_tokens` and the
current `query_start_loc` (`v1/worker/gpu/model_runner.py:1205-1213`). It builds
the per-request values as

`query_len = query_start_loc[i + 1] - query_start_loc[i]`

and

`seq_len = Cnext + query_len`

in `v1/worker/gpu/input_batch.py:307-339`. Those tensors are passed into common
attention metadata. KVarN reads exact `seq_lens`, derives query lengths from
`query_start_loc_cpu`, and computes the boundary as their difference
(`kvarn_attn.py:599-620,675-684,801-807`). Consequently, on the first verify
after rejections it receives `seq_len = accepted_after_rejection + current_Q`
and `query_len = current_Q`; its committed value is exactly
`accepted_after_rejection`.

The 0.27 core has the same construction at
`v1/worker/gpu/input_batch.py:248-280`, the same accepted delta at lines
489-499, and calls it from `v1/worker/gpu/model_runner.py:920-1008`. Neither
runner patch changes those formulas. The port changed graph classification,
not the sequence-length arithmetic supplied to the attention builder.

Therefore the normal 0.28 path does not include rejected rows in KVarN's
committed boundary. The drafter's separate input preparation also removes the
rejected suffix from `valid_ctx_end`, marks invalid context and query slots with
`PAD_SLOT_ID`, and reports an absolute next sequence length
(`patches/dflash2-backport.patch:238-301`). That historical backport is retired
on 0.28 because native DFlash2 already contains this path, but the logic was not
deleted by the port.

There is still no defense in KVarN if those inputs are wrong at runtime. The
builder has no accepted-token bitmap. If `seq_len - query_len` is too large, a
full tile containing rejected KV can satisfy the walk at
`kvarn_attn.py:801-815`, be quantized and have its fp16 slot freed at lines
845-869. On the next step, a reused block id can acquire a new empty pool slot
at lines 879-911 and receive only the newly scheduled writes. The code therefore
does allow the rejected-row overwrite to land in what it now believes is a
committed block. That is a real corruption mechanism conditional on bad or
stale metadata, but it is not what the static 0.28 formulas produce.

### 4. Ranked regression candidates

1. The 0.28 final-prefill classifier in
   `GPUModelRunner.gather_batch_req_state`. This is the narrowest lost guarantee
   relative to the passing fork. It is DFlash-specific in this deployment
   because DFlash uses the uniform captured verify route while huge-context MTP
   is pinned to piecewise mode (`single-user/start_qwen.sh:575-584`). It is
   KVarN-specific because a wrongly replayed step can poison persistent slot and
   flush state, while ordinary KV formats overwrite native cache rows without a
   permanent fp16-to-int4 commit boundary. It runs before any output consumer,
   does not require prefix reuse, and is identical on both boxes.

2. More generally, the 0.28 uniform FULL graph replay seam between the runner's
   persistent input buffers and KVarN's persistent metadata buffers. KVarN
   deliberately updates captured `seq_lens`, block tables, and verify-plan
   buffers in place (`kvarn_attn.py:638-644,916-984`). Any 0.28 ordering or
   descriptor reuse that replays before those updates has exactly the same
   stale-boundary consequence even when the prefill classifier is correct.
   This has the same DFlash, KVarN, consumer, prefix, and hardware fit as
   candidate 1, but it is broader and has no single changed line in the runner
   patch.

3. The 0.28 native selector and rejection-sampler bridge at
   `patches/dflash2-lookup-drafting.patch:150-228`. This is the largest
   DFlash-only numerical change that still executes with lookup and adaptive
   mode off. The passing native KV tiers and failing KVarN tier are compatible
   with proposal sensitivity to KVarN quantization noise, and the three old NaN
   defenses do not prove the new gumbel and truncation bridge equivalent. It is
   below the graph candidates because greedy runs do not consume q, and because
   the retained clamp, zero initialization, and score sanitization already
   cover the previously demonstrated failure.

4. The omitted old `Attention.get_kv_cache_spec` shared-page hunk. It is a real
   port difference and can alter DFlash plus KVarN physical page geometry on
   both boxes. It ranks last because the later block-promotion patch explicitly
   replaces its purpose, the measured k=7 geometry is already promoted, and a
   geometry-only issue has no direct reason to respect target verify type while
   MTP remains mostly clean.

The Mamba add-request hunk is not in the four. It is functionally retained, and
the rejection update is downstream core logic shared by cache tiers and
speculators. The current evidence gives it a worse fit than every item above.
